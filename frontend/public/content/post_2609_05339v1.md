# 에이전트의 기억은 모델 업그레이드 후에도 살아남을 수 있는가? 기억 이식성에 대한 통제된 연구

> **원본 논문 정보**
> - **제목:** Does Your Agent's Memory Survive a Model Upgrade? A Controlled Study of Memory Portability
> - **저자:** Ankit Goyal, Jaideep Ray
> - **발행일:** 2026-09-04
> - **PDF 링크:** [Does Your Agent's Memory Survive a Model Upgrade? A Controlled Study of Memory Portability](https://arxiv.org/pdf/2609.05339v1)


## ✨ 3줄 핵심 요약
*   모델 업그레이드 시 기존 기억 저장소를 재사용할 경우, 모델 해석 차이와 정보 손실로 인해 에이전트 성능이 심각하게 저하될 수 있습니다.
*   고정 스키마 지식 그래프(KG-fixed)는 모델 변경에도 안정적이나, 자연어 요약 노트(NOTES)는 모델 의존도가 매우 높습니다.
*   안정적인 기억 이식을 위해 임베딩 공간의 엄격한 분리, 기억 복구 경로 확보, 그리고 원본 기록(Raw History) 보존이 필수적입니다.

## 📖 쉽게 풀어쓴 1분 핵심
AI 에이전트의 '기억'은 보통 모델이 학습한 내용과는 별도로 저장됩니다. 그런데 모델을 더 똑똑한 버전으로 업그레이드할 때, 예전에 저장해둔 기억을 새 모델이 제대로 이해하지 못하는 문제가 발생합니다. 본 연구는 4가지 기억 저장 방식(원문 보존, RAG, 요약 노트, 지식 그래프)을 비교하여, 모델이 바뀌어도 기억이 안전하게 유지되는지 분석했습니다. 결과적으로 단순히 모델만 교체하는 것은 위험하며, 원본 데이터를 확보하거나 구조화된 방식을 사용하는 것이 성능 유지에 결정적임을 확인했습니다.

## 🎯 배경 및 문제점
모델은 수시로 업그레이드되지만, 축적된 기억 저장소는 그대로 남아있는 경우가 많습니다. 이때 발생하는 주요 문제는 다음과 같습니다.
*   **모델 의존성:** 새 모델이 과거의 요약된 노트를 다르게 해석함.
*   **기술적 충돌:** 임베딩 버전 혼재로 인한 검색 실패.
*   **복구 불능:** 원본 데이터 없이 요약된 정보만 남아있을 경우, 업그레이드 후 발생한 오류를 수정할 방법이 없음.

## 💡 핵심 기술 및 아키텍처
연구진은 4가지 기억 저장 방식을 48개의 합성 기록을 사용하여 테스트했습니다.
*   **LC-RAW:** 전체 대화 기록을 원문 그대로 저장.
*   **RAG:** 기록을 조각내어 필요할 때마다 검색하여 사용.
*   **NOTES:** 모델이 압축한 자연어 요약본을 저장.
*   **KG-fixed:** 고정된 스키마에 따라 사실관계를 지식 그래프 형태로 저장.

## 📊 실험 결과 분석
*   **KG-fixed의 안정성:** 작성자가 변경되어도 정확도 변화가 +0.0004±0.0020에 불과해 매우 안정적임.
*   **NOTES의 높은 모델 의존성:** 방향에 따라 정확도가 +9.91%p에서 -13.28%p까지 변동하는 비대칭적 성능 변화를 보임.
*   **RAG의 한계:** 50/50 혼합 인덱스 사용 시, 전체 재임베딩(11.90%p 개선)에 비해 4.96%p 개선에 그쳐 성능 손실이 큼.
*   **원인 분석:** NOTES 성능 저하의 80%(0.467±0.014)는 초기 요약 과정에서의 정보 손실이며, RAG 성능 저하의 81%(0.364±0.012)는 검색 실패로 판명됨.
*   **복구 성공률:** 원본 기록을 보존한 경우 48건 중 34건에서 복구가 성공했으나, '저장소 전용(store-only)' 수리는 모든 사례에서 90% 복구 목표 달성에 실패함.

## 🌍 세상에 미치는 영향 & 실무 적용 사례
*   **기억 이식 전략:** 모델 교체 시 '단순 교체'가 아닌 '데이터 마이그레이션' 관점으로 접근해야 함.
*   **실무 권고:** 
    1. 새 모델로 기존 저장소를 반드시 사전 테스트할 것.
    2. 벡터 인덱스는 부분 업데이트 대신 완전히 재구축할 것.
    3. 정책이 허용한다면 문제 발생 시 복구를 위해 원본 소스 기록을 반드시 유지할 것.
    4. 기억 손실이 발생한 지점(저장, 검색, 읽기)을 정확히 진단할 것.
