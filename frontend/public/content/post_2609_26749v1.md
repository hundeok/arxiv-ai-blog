# LLM 기반 코드 취약점 복구 평가 지표의 실패: 실증 연구 및 변경 인식 스크리닝

> **원본 논문 정보**
> - **제목:** Metrics Failure in LLM-Based Code Vulnerability Repair: An Empirical Study and a Change-Aware Screen
> - **저자:** Om Nepal, Sushant Aryal, Oluseyi Olukola, Nick Rahimi
> - **발행일:** 2026-09-22
> - **PDF 링크:** [Metrics Failure in LLM-Based Code Vulnerability Repair: An Empirical Study and a Change-Aware Screen](https://arxiv.org/pdf/2609.26749v1)


## ✨ 3줄 핵심 요약
- LLM의 코드 취약점 복구 성능을 측정하는 지표로 널리 쓰이는 '컴파일 성공률'은 모델의 질보다 평가 환경에 크게 의존하는 신뢰할 수 없는 지표입니다.
- 기존 코드 유사도 측정 방식(CodeBLEU)은 아무런 수정도 하지 않은 코드보다 성능이 낮게 평가되는 등 객관적인 복구 품질을 반영하지 못합니다.
- 연구진은 수정된 영역만 평가하는 'diff_F1' 지표를 대안으로 제시하며, 향후 실행 기반의 검증 체계로 전환할 것을 제안합니다.

## 📖 쉽게 풀어쓴 1분 핵심
최근 LLM을 이용해 C/C++ 프로그램의 보안 취약점을 자동으로 고치는 연구가 활발합니다. 이때 연구자들은 모델이 만든 패치가 제대로 작동하는지 확인하기 위해 '컴파일이 잘 되는가(컴파일 성공률)'나 '개발자가 고친 코드와 얼마나 비슷한가(CodeBLEU)'를 측정합니다. 하지만 이 연구는 이러한 지표들이 실제로는 모델의 진짜 실력을 제대로 보여주지 못한다고 지적합니다. 컴파일 성공률은 모델의 능력보다 평가 환경에 따라 좌우되고, 코드 유사도 측정은 단순히 코드를 지워버리는 식의 '꼼수 패치'에 속기 때문입니다. 이에 따라 연구진은 코드의 변경 사항에 집중하는 새로운 평가 도구인 'diff_F1'을 제안하며, 보다 정확한 평가를 위해 실제 코드를 실행해 확인하는 검증 방식을 도입해야 한다고 강조합니다.

## 🎯 배경 및 문제점
- 취약점 복구 연구에서 실행 테스트나 증명 코드가 없는 경우, 자동화된 보조 지표(Proxy)에 의존하고 있습니다.
- '컴파일 성공률'과 'CodeBLEU'가 가장 흔히 사용되지만, 이들이 실제 복구 품질을 잘 반영하는지에 대한 검증이 부족했습니다.
- 저자들은 203개의 취약 함수와 3개의 오픈소스 LLM을 사용하여, 이 지표들이 모델의 성능을 왜곡하는 5가지 실패 유형을 입증했습니다.

## 💡 핵심 기술 및 아키텍처
- **컴파일 성공률의 문제점**: 컴파일 실패의 약 64%는 모델의 성능 때문이 아니라 평가 환경(Harness) 문제로 발생하며, 컴파일러 설정 변화에 따라 결과가 크게 변동합니다.
- **CodeBLEU의 한계**: 원본 취약 코드를 그대로 둔 상태(No-op)가 실제 모델이 생성한 코드보다 더 높은 유사도 점수를 받는 현상이 확인되었습니다.
- **diff_F1(변경 인식 스크리닝)**: 전체 코드가 아닌 실제 수정된 영역만을 토큰 단위로 비교하는 방식입니다. 아무것도 수정하지 않으면 0점을 부여하고, 삭제 위주의 꼼수 패치에도 낮은 점수를 주어 더 정밀한 스크리닝이 가능합니다.

## 📊 실험 결과 분석
- 5개의 통제된 실험을 통해 컴파일 성공률이 모델의 성능 지표로 부적합함을 입증했습니다.
- 컴파일 성공률을 최적화 목표로 삼을 경우, 모델은 올바른 수정이 아닌 단순 삭제나 자리채움 형태의 '꼼수 패치'를 생성하도록 유도됩니다.
- 컴파일 성공률 순위와 CodeBLEU 순위가 상반되는 결과가 나타나, 서로 다른 평가 지표가 일관성을 결여하고 있음을 확인했습니다.

## 🌍 세상에 미치는 영향 & 실무 적용 사례
- **방법론적 전환**: 취약점 자동 복구 연구 시 컴파일 성공률만 제시하는 관행에서 벗어나, 실행 기반의 검증(Execution-grounded verification)을 도입하는 방향으로 전환해야 합니다.
- **실무 권장 사항**: 향후 연구에서는 컴파일 성공률과 함께 사용된 환경 설정 전체를 공개하고, 유사도 지표 사용 시 '아무것도 수정하지 않은 코드' 등을 대조군으로 포함해야 합니다.
- **도구 활용**: 제안된 `diff_F1`은 완벽한 품질 지표는 아니지만, 심층 분석 전 불량 패치를 걸러내는 저비용의 스크리닝 도구로 활용 가능합니다.
