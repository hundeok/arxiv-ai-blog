LLM 디컴파일러가 더 많이 재컴파일할수록 보존력은 떨어지는 현상에 대하여

LLM 디컴파일러가 더 많이 재컴파일할수록 보존력은 떨어지는 현상에 대하여

LLM 디컴파일러가 더 많이 재컴파일할수록 보존력은 떨어지는 현상에 대하여

> **원본 논문 정보**
> - **제목:** When LLM Decompilers Recompile More and Preserve Less
> - **저자:** Chang Liu, Edward Raff, Kristopher Micinski
> - **발행일:** 2026-09-04
> - **PDF 링크:** [When LLM Decompilers Recompile More and Preserve Less](https://arxiv.org/pdf/2609.05370v1)


✨ 3줄 핵심 요약
- LLM 기반 디컴파일러는 재컴파일 가능성을 높이지만, 정작 원본 코드의 동작을 정확히 보존하는 데는 한계를 보입니다.
- 기존의 '재컴파일 및 테스트 통과' 중심 평가 방식은 원본 코드와의 동작 불일치나 보안 취약점 소실을 감지하지 못합니다.
- 연구진은 퍼징(Fuzzing) 기반의 'Decompile-Diverge' 평가 체계를 제안하여, 컴파일은 성공하더라도 실제 동작은 원본과 다른 코드들을 성공적으로 식별했습니다.

📖 쉽게 풀어쓴 1분 핵심
기존의 디컴파일러(Ghidra 등)는 코드를 해석하지 못하면 모르는 부분임을 표시했지만, 최신 LLM 디컴파일러는 그 자리를 그럴싸한 코드로 임의로 채워 넣어 재컴파일 성공률을 높입니다. 하지만 연구 결과, 이렇게 생성된 코드는 보기엔 깔끔해도 원본과 다르게 동작하거나, 원래 포함되어 있던 보안 취약점을 감쪽같이 사라지게 만드는 '동작 오류'를 일으킵니다. 연구진은 입력값을 다양하게 변형하여 실행해보는 방식으로 원본과 디컴파일된 코드의 동작을 비교하는 새로운 평가 기법을 개발했습니다.

🎯 배경 및 문제점
- **평가 지표의 함정:** 현재 LLM 디컴파일러는 '재컴파일 성공 여부'와 '제공된 테스트 케이스 통과 여부'로 성능을 평가받습니다.
- **불완전한 검증:** 이 방식은 통과했더라도 입력값이 조금만 달라지면 원본과 다르게 동작할 수 있고, 무엇보다 코드 내의 보안 취약점이 의도치 않게 삭제되어도 이를 인지하지 못하는 치명적인 한계가 있습니다.

💡 핵심 기술 및 아키텍처
- **Decompile-Diverge:** 고정된 테스트 대신 퍼징(fuzzing)을 통해 원본 코드의 행동을 학습하고, 디컴파일된 코드에 동일한 입력을 넣어 결과를 비교하는 행동 오라클(Behavioral Comparison Oracle)입니다.
- **평가 방식:** 생성된 드라이버를 통해 입력값을 자동으로 주입하고, 함수 실행 후의 상태(post-state)를 요약하여 원본과 비교합니다.
- **데이터 분석:** 300개의 실제 GitHub 라이브러리 함수와 287개의 CVE 기반 취약점 함수를 대상으로 성능을 검증했습니다.

📊 실험 결과 분석
- **성능의 역설:** 가장 뛰어난 모델의 경우 Ghidra의 빌드 성공률을 75%에서 90%로 향상시켰지만, 실제 원본 코드와의 동작 일치율은 74%에서 62%로 오히려 하락했습니다.
- **취약점 소실:** CVE(보안 취약점) 함수 평가 시, 최대 1/10의 모델 결과물에서 취약점이 사라지는 'Crash Absence' 현상이 발견되었습니다.
- **발산 원인:** LLM이 모르는 부분을 스스로 지어낸 코드(introduced fields, types, callees)로 채우면서 원본과 다른 동작이 발생함이 소스 레벨 분석을 통해 확인되었습니다.
- **정량적 수치:** 테스트를 통과한 결과물 중 4.9%는 전체적으로, 특정 시스템에서는 최대 13%까지 원본 코드와 동작이 다르게 나타났습니다.

🌍 세상에 미치는 영향 & 실무 적용 사례
- **보안 분석의 신뢰성:** 악성코드 분석이나 취약점 점검 시 LLM 디컴파일러를 맹신할 경우, 실제 존재하는 보안 결함을 놓칠 위험이 있음을 경고합니다.
- **평가 패러다임 전환:** 단순히 "코드가 잘 만들어지는가"를 넘어 "원본과 동일하게 동작하는가"를 평가하는 것이 보안 및 소프트웨어 엔지니어링 도구 개발의 핵심임을 제시합니다.
- **실무 권고:** 디컴파일된 코드를 통합하거나 분석할 때, 자동화된 재컴파일 평가 외에도 이번 연구에서 제안된 것과 같은 엄격한 행동 기반 비교 검증 단계가 필수적입니다.
